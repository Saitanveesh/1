# ADR 0053: Release SBOM gate

## Status

Accepted

## Context

ADR 0050 requires release packaging to produce software-bill-of-materials evidence before publication. ADR 0052 now provides deterministic exact-byte artifact manifests, but a digest manifest identifies bytes rather than the software components and dependencies represented by those bytes.

MON therefore needs an SBOM gate that is generated by trusted CI from the same immutable source revision and final release payload used by the release manifest. It must not depend on an operator workstation, production telemetry, or tenant/site credentials.

## Decision

Release CI MUST generate a CycloneDX JSON SBOM for every releasable payload before publication. SBOM generation is a hard gate: a missing SBOM, generator failure, invalid CycloneDX document, or inability to associate the evidence with the immutable release source revision fails the release.

The SBOM is generated in CI only. The generator must inspect the release build context and declared/runtime dependencies rather than accepting a hand-maintained component list. The generated SBOM is itself a release artifact and therefore MUST be present before `manifest.json` is generated so ADR 0052 records the exact SBOM bytes and SHA-256 digest.

The release order is:

1. check out the immutable release commit;
2. build release payloads in trusted CI;
3. generate and validate the CycloneDX JSON SBOM;
4. place the SBOM beside the final release payload;
5. generate `manifest.json` over the final payload and SBOM bytes;
6. verify the manifest;
7. apply the separate provenance/signing gate;
8. publish only if all required gates are green.

SBOM generation must not execute release binaries. It must not embed environment secrets, tenant/site credentials, telemetry, absolute build-host paths, or mutable branch names as release identity. Any future exception requires a new ADR and explicit security review.

The SBOM is inventory evidence, not authenticity evidence and not a vulnerability verdict. Provenance/signing remains a separate mandatory gate under ADR 0050.

## Consequences

- Every published MON release will carry machine-readable component inventory evidence.
- The exact SBOM bytes are covered by the deterministic release manifest.
- Release packaging fails closed when SBOM evidence cannot be generated or validated.
- Operators do not need to trust or run an unvalidated binary on a laptop to obtain release inventory evidence.
- Vulnerability scanning may consume the SBOM later, but scanner findings and policy are intentionally separate from SBOM construction.
